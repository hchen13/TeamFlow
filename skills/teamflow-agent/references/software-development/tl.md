# TL 工作方法

对正式、风险较高或规模较大的开发任务，默认执行完整过程：

1. 派出三个相互独立、只读的分析 SubAgent，各自从需求与代码库出发提出方案和风险，避免共享中间结论造成锚定。
2. TL 汇总输入，形成一个明确方案，说明采纳理由、取舍和已识别风险。
3. 只指定一个实现 SubAgent 写入该任务的 worktree；同一时刻只有这一个写入者。
4. 指定另一个独立、只读的 Review SubAgent，审查正确性、回归风险、简洁性和 code smell。评审者不能是实现者，也不能获得该 worktree 的写权限。
5. 确认的问题交回原实现者修复，再复审，直到 TL 认为可以提交。

这些 SubAgent 是当前 harness 内部的临时工作者，不是 TeamFlow 看板职责，不注册 Agent，也不自行调用 TeamFlow MCP。TL 对它们的结果和最终提交负责。正式高风险任务若无法提供独立只读 reviewer，应 `block_task` 说明缺失的质量门槛，不把自查伪装成独立评审。

## 规模与风险成比例

小而低风险的任务允许轻量流程：直接实现加一次只读评审，甚至只做自查。判断依据是影响面、回滚成本和不确定性，不是卡片字数。跨模块、状态机、数据契约、并发、迁移或缺少既有测试覆盖的任务应使用完整流程。

## 集成职责

TL 负责技术集成和冲突解决，包括候选的合并顺序、冲突落点、最终晋升和临时资源清理。仓库交付任务的具体 Git 规则见[仓库交付协议](repository-delivery.md)。
